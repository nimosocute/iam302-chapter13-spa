## 3. Cơ chế hoạt động chi tiết

### 3.1. Cơ chế chụp màn hình (Desktop Capture - `0x00401070`)
1. Lấy kích thước màn hình:
   - `GetSystemMetrics(0)`: lấy `SM_CXSCREEN` (chiều rộng màn hình).
   - `GetSystemMetrics(1)`: lấy `SM_CYSCREEN` (chiều cao màn hình).
2. Lấy handle cửa sổ Desktop và Device Context (DC):
   - `GetDesktopWindow()` -> lưu vào biến toàn cục tại `0x004078CC`.
   - `GetDC(hDesktop)` -> lưu vào `0x004078C8`.
3. Tạo Memory DC và tương thích bitmap:
   - `CreateCompatibleDC(hdcScreen)` -> tạo Memory DC `[ebp-0x4c]`.
   - `CreateCompatibleBitmap(hdcScreen, width, height)` -> tạo bitmap `[ebp-0x18]`.
   - `SelectObject(memDC, hBitmap)`.
4. Sao chép điểm ảnh màn hình:
   - `BitBlt(memDC, 0, 0, width, height, hdcScreen, 0, 0, SRCCOPY)` (`0x00CC0020`).
5. Trích xuất mảng byte điểm ảnh:
   - Gọi `GetDIBits` với định dạng 32 bit-per-pixel (RGB 32-bit).
6. Đóng gói thành định dạng Bitmap file (.BMP) trong bộ nhớ:
   - Ghi 14 bytes `BITMAPFILEHEADER`:
     - `bfType` = `0x4D42` (`'BM'`) tại VA `0x004011DD`.
     - `bfSize` = kích thước ảnh + 54 bytes (`0x36`).
     - `bfOffBits` = `0x00000036` (54 bytes).
   - Ghi 40 bytes `BITMAPINFOHEADER`: `biSize` = `0x28` (40), `biPlanes` = 1, `biBitCount` = 32 (`0x20`), `biCompression` = 0 (`BI_RGB`).
   - Sao chép toàn bộ mảng dữ liệu DIBits phía sau offset `0x36`.
   - Trả về con trỏ vùng nhớ `GlobalAlloc` và kích thước tổng `len = 54 + (width * height * 4)`.

### 3.2. Cơ chế mã hóa: Biến thể Rabbit Stream Cipher (Zero-State & Modified Constant)

Khác với chuẩn RFC 4503, tác giả `Lab13-02.exe` cài đặt một biến thể riêng biệt với hai điểm sai khác cốt tử:

1. **Khởi tạo Zero-State (Không Key Schedule)**:
   - Tại `0x00401825` - `0x0040182d`, malware cấp phát 68 bytes (`0x44`) trên stack và gọi `memset(ctx, 0, 0x44)`.
   - Mã độc **hoàn toàn bỏ qua quy trình Key Setup chuẩn** của Rabbit (RFC 4503 Section 3.2: chia khóa 128-bit, mở rộng, tính toán 4 vòng khởi động hệ thống warmup).
   - Do đó, mọi trạng thái $X_0 \dots X_7 = 0$, $C_0 \dots C_7 = 0$, $b = 0$.

2. **Hằng số Counter bị sửa đổi (`0x4D34D35D`)**:
   - Trong chuẩn RFC 4503, vector hằng số là:
     $A = [0x4D34D34D, 0xD34D34D3, 0x34D34D34, \dots]$
   - Trong binary `Lab13-02.exe`, các lệnh tại `0x40131B`, `0x40137B`, `0x4013DB` sử dụng trực tiếp:
     `lea ecx, [eax + ecx + 0x4d34d35d]`
   - Do đó, hằng số tại chỉ số $A[0], A[3], A[6]$ là **`0x4D34D35D`** (lệch $+0x10$ so với RFC `0x4D34D34D`):
     - $A[0] = \text{0x4D34D35D}$
     - $A[1] = \text{0xD34D34D3}$ (`-0x2cb2cb2d`)
     - $A[2] = \text{0x34D34D34}$
     - $A[3] = \text{0x4D34D35D}$
     - $A[4] = \text{0xD34D34D3}$
     - $A[5] = \text{0x34D34D34}$
     - $A[6] = \text{0x4D34D35D}$
     - $A[7] = \text{0xD34D34D3}$

3. **Keystream sinh ra và Nhận dạng Header**:
   - Keystream 16 bytes đầu tiên của `Lab13-02`:
     `a0 a3 96 2c 73 cc 46 23 ab 0a a4 74 f1 60 de 42`
   - Khi mã hóa file BMP có 2 byte đầu `'BM'` (`0x42 0x4D`):
     - Byte 0: `0x42 ^ 0xa0 = 0xe2`
     - Byte 1: `0x4d ^ 0xa3 = 0xee`
   - **Đặc trưng nhận diện file artifact của Lab13-02**: Mọi file `temp%08x` bị mã hóa luôn bắt đầu bằng 2 byte ma thuật **`0xE2 0xEE`**.

4. **Bảo toàn phần dư đuôi (Tail Preservation)**:
   - Kích thước BMP là $54 + (W \times H \times 4)$; artifact thực tế dư **2 bytes** khi chia 16.
   - Trong `0x401739`, malware xử lý trọn khối 16 bytes trong bộ nhớ khi $offset < len$, không có nhánh xử lý phần dư riêng.
   - Tại `0x4018b0`, malware nạp chiều dài ban đầu; lệnh gọi `sub_401000` tại `0x4018b8` dẫn đến `WriteFile` ghi đúng $len$ ra đĩa.
   - Decoder chỉ XOR các byte thực sự tồn tại ở khối cuối. Kết quả giữ chiều dài, không chèn padding; chưa có plaintext độc lập để chứng minh bằng nhau byte-for-byte.

### 5.2. Xác thực cấu trúc BMP Header qua Pillow & Struct Unpack

- **Thông số Header (54 bytes)**:
  - `bfType`: `BM` (`0x4D42`)
  - `bfSize`: **`5,436,114` bytes** (khớp hoàn toàn với kích thước file thực tế trên đĩa)
  - `bfOffBits`: `54` bytes (`0x00000036`)
  - `biSize`: `40` bytes (`0x00000028` - `BITMAPINFOHEADER`)
  - `biWidth`: `1505` pixels
  - `biHeight`: `903` pixels
  - `biPlanes`: `1`
  - `biBitCount`: `32` bits/pixel (BGRA 4 bytes/pixel)
  - `biCompression`: `0` (`BI_RGB` - không nén)
  - `biSizeImage`: `5,436,060` bytes
- **Kiểm toán kích thước**:
  $$\text{Pixel Data} = 1505 \times 903 \times 4 = 5,436,060\text{ bytes}$$
  $$\text{Tổng kích thước file} = 54 + 5,436,060 = 5,436,114\text{ bytes}$$
  $$\text{Sai lệch}: 0\text{ byte}$$

### 5.3. Phân biệt quan trọng: Row Padding Zeros vs. File Tail Unaligned Bytes
1. **Row Padding trong ảnh 32bpp**:
   - Theo chuẩn Windows BMP, mỗi dòng quét (scanline) phải căn chỉnh biên 4 bytes (`DWORD boundary`).
   - Công thức stride: $\text{stride} = \lfloor \frac{\text{width} \times 32 + 31}{32} \rfloor \times 4 = \text{width} \times 4$.
   - Vì mỗi pixel 32bpp chiếm đúng 4 bytes, mỗi dòng quét dài $1505 \times 4 = 6020$ bytes (đã chia hết cho 4). Do đó, **padding zeros ở cuối mỗi dòng quét là 0 byte**.
2. **Phần dư của nhóm keystream 16-byte trong stream cipher**:
   - Toàn bộ file có kích thước: $5,436,114 \pmod{16} = 2\text{ bytes}$.
   - Khối cuối cùng của file chỉ có **2 bytes**.
   - Mã độc sử dụng hàm `WriteFile` với độ dài thực tế `len = 5,436,114` (không chèn zero-padding ở mức file).
   - Trình giải mã `decrypt_rabbit.py` sinh nhóm keystream 16 bytes cuối cùng nhưng chỉ lấy đúng $rem = 2$ bytes để XOR với 2 bytes cuối của ciphertext. Kết quả có kích thước $5,436,114$ bytes, header hợp lệ và hiển thị được trong Paint. Không có checksum plaintext gốc để đối chiếu.
